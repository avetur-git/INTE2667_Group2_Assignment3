# infra/ - Infrastructure as Code (REQ-06) and rollback drill (REQ-16)

Firewall rules, network layout and database access for the production
deployment, written in Terraform. Nothing here can reach `main` without a
reviewed pull request that passes the automated policy checks.

| Control | Where |
|---|---|
| Network, firewall rules, exposed ports, DB users as code | this folder |
| Pull request required, 1 approval, no direct pushes, no force pushes | `.github/rulesets/main.json` (imported into GitHub, see below) |
| Infrastructure changes need the platform owner's approval | `.github/CODEOWNERS` |
| Config scan, fails on HIGH or CRITICAL findings | `.github/workflows/iac.yml`, job **IaC security scan (tfsec)** |
| Proof that the scan catches an open database port | job **IaC scanner self-test**, fixture `tests/iac/insecure/main.tf` |

## What is defined

```
internet --443--> ALB (public subnets) --5000--> app (private subnets) --5432--> PostgreSQL (db subnets)
```

| File | Contents |
|---|---|
| `network.tf` | VPC, public/app/db subnets in two AZs, only the public subnets route to the internet, a network ACL that limits the db subnets to PostgreSQL from the app subnets, VPC flow logs |
| `security_groups.tf` | The firewall rules. One described rule per allowed flow. Only the load balancer takes traffic from an address range (`0.0.0.0/0` on 443); every other tier only accepts its neighbour's security group. The database has no outbound rules |
| `load_balancer.tf` | HTTPS-only listener with TLS 1.2/1.3, invalid headers dropped |
| `database.tf` | RDS PostgreSQL: not public, encrypted with a rotating KMS key, TLS forced, IAM authentication, master password generated by RDS and stored in Secrets Manager, connection and DDL logging |
| `db_users.tf` | Database users and grants (below) |
| `rollback.py` | REQ-16 rollback drill script (see [Rollback](#rollback-req-16)) |

Database users, all logging in with IAM tokens (no passwords):

| User | Database | Can do |
|---|---|---|
| `evoting_app` | `evoting` | read/write the app tables; `audit_logs` is SELECT and INSERT only (append-only) |
| `evoting_ballot_store` | `evoting_ballots` | SELECT and INSERT on `ballots` and `spent_tokens`; ballots can never be updated or deleted |
| `evoting_auditor` | `evoting` | SELECT on `audit_logs` only |
| `evoting_owner` | both | owns the schema, cannot log in (migrations only) |

`PUBLIC`'s default CONNECT and CREATE rights are revoked, so only these grants
apply. The two databases match the two SQLAlchemy binds (`DATABASE_URL`,
`BALLOT_DATABASE_URL`), which keeps ballots apart from voter data (REQ-01).

Prototype limits: the local and Docker builds still use SQLite, and this
configuration is validated and scanned in CI but not applied to an AWS account.
The app containers (ECS or similar) are left to REQ-08/REQ-09; they attach to
`app_security_group_id` and `app_subnet_ids` from `outputs.tf`.

## Changing infrastructure

1. Branch from `main` and edit the `.tf` files.
2. Run locally if you have the tools: `terraform fmt -recursive`, `terraform init -backend=false`, `terraform validate`, `tfsec .`
3. Open a pull request. The **IaC** workflow runs and GitHub requests a review from the code owner (`@avetur-git`).
4. It can merge only when every required check is green and the code owner has approved. A new push after approval needs a new approval.

If tfsec flags something that is intended (the public load balancer, for
example), the exception goes directly above the resource:

```hcl
#tfsec:ignore:<check-id> Reviewed exception (REQ-06): <why this is safe>
resource "..." "..." {
```

The pipeline fails any `tfsec:ignore` that has no `Reviewed exception`
justification, and lists every exception in the job summary for the reviewer.

## Turning on branch protection (repo admin, once)

GitHub only enforces rulesets on a **private** repository if the owner's
account has GitHub Pro (free with the GitHub Student Developer Pack) or the
repo belongs to an organisation on a paid plan. Public repositories get them
on the free plan.

1. Merge this change first, so the workflows have run once and their check names exist.
2. **Settings > Rules > Rulesets > New ruleset > Import a ruleset**, choose `.github/rulesets/main.json`, then **Create**.
3. Check that **Bypass list** is empty, so admins cannot push directly either.

The ruleset blocks deleting and force-pushing `main`, requires a pull request
with 1 approval from a code owner (stale approvals dismissed), and requires the
IaC and CI checks to pass on an up-to-date branch.

Because a code owner cannot approve their own pull request, infrastructure PRs
opened by `@avetur-git` need a second code owner. Add one to `.github/CODEOWNERS`
before that happens.

## Demonstrating the acceptance criteria

**Direct push to main is rejected**

```bash
git checkout main && git pull
git commit --allow-empty -m "test: direct push"
git push origin main
# remote: error: GH013: Repository rule violations found for refs/heads/main.
# remote: - Changes must be made through a pull request.
git reset --hard origin/main   # drop the test commit
```

**Infrastructure PR cannot merge without approval**: open any PR that changes a
file in `infra/`. The PR page shows "Review required" and "Waiting on code owner
review from avetur-git", and the merge button is disabled.

**Insecure rule fails the pipeline**: on a branch, open the database to the
internet in `security_groups.tf`:

```hcl
resource "aws_security_group_rule" "db_in_anywhere" {
  type              = "ingress"
  description       = "TEST: PostgreSQL from anywhere"
  security_group_id = aws_security_group.db.id
  protocol          = "tcp"
  from_port         = 5432
  to_port           = 5432
  cidr_blocks       = ["0.0.0.0/0"]
}
```

Open a PR. **IaC security scan (tfsec)** fails with CRITICAL
`aws-ec2-no-public-ingress-sgr` and the PR cannot be merged. Close the PR
without merging.

## Rollback (REQ-16)

Every change to this folder is committed to Git, so the rollback pipeline can
restore the previous good state.

### Rollback script

Run the prototype rollback from the repository root:

```bash
python EVotingPlatform/infra/rollback.py \
  --repo . \
  --redeploy-command "docker compose up -d --build" \
  --health-url http://localhost:5000/health \
  --max-duration-seconds 900
```

The script does the following:

- checks that the repository has a previous commit to return to
- runs `git revert HEAD` so the bad change is preserved in history
- redeploys the service
- runs the health check
- fails if the service is not healthy or if the rollback exceeds 900 seconds
- records the duration and the audit event

### Drill procedure

1. Create or identify a bad infra change in a branch or temporary commit.
2. Trigger the `Rollback drill` workflow manually or wait for the scheduled cron job.
3. Review the workflow output and the Git log to verify a revert commit was created.
4. Confirm `/health` is healthy after deployment.
5. If the rollback exceeds 15 minutes, stop the drill, treat it as a failed recovery, and escalate to the operations owner.

The rollback drill is expected to be run on a schedule (for example weekly or monthly) and after any major infra change.

### Cloud deployment notes

The production version of this pipeline is the same sequence executed against the cloud environment:

- apply the last known-good infrastructure state with Terraform/OpenTofu
- require manual approval before the destructive apply step in the deployment environment
- run health checks and target-group / service validation after the change
- alert the on-call operations user if the rollback or health check fails
- keep the Git history as the audit trail for the recovered state
